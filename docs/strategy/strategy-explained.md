# C′戦略の詳しい解説

## 1. 何を解こうとしているか

ポケモンカードでは、盤面だけでなく相手の手札、山札、裏向きサイドが見えません。同じ公開盤面でも、相手が次のターンに進化カードを持っている場合と、エネルギーしか持っていない場合では最善手が変わります。さらに、目先で30ダメージ多い行動が、次ターンのエネルギーやアタッカーを失って最終的な勝率を下げることもあります。

本agentは、この問題を次の4層に分けます。

1. 観測履歴から、あり得る相手デッキを推定する。
2. 60枚の整合性を保ったまま、見えないカード配置を1つ作る。
3. Transformerで局面と合法手を評価する。
4. 24回のPUCT探索で短期行動と長期勝敗をつなぎ、最も訪問された手を選ぶ。

この最終方式を `C′: history-consistent single-determinization PUCT` と呼びます。

## 2. 用語

### 状態と観測

**状態**は、本来の手札・山札・サイドまで含むゲーム全体です。**観測**は、現在のプレイヤーに見える部分だけです。cabtは盤面、手札、捨て札、ログ、合法な選択肢を`obs_dict`として渡しますが、相手の非公開カードは個数しか分かりません。

### belief state

**belief state**は、「見えていない状態がどのような可能性を持つか」という推定です。本実装は確率分布をニューラルネットワークで学習する方式ではありません。公開された相手カードを物理カードのserial単位で履歴へ蓄積し、それらを含む60枚デッキ候補を検索します。

候補が複数なら、まず観測カードをすべて含むものを選び、その中で過去勝利数の多い候補を優先します。完全一致候補がなければ観測カードとの一致枚数が最大の候補を選び、観測済みカードを必ず含む60枚へ補正します。したがって「確率的に正しい」とは限りませんが、観測したカードが推定デッキから消える矛盾は防ぎます。

### 決定化

**決定化**は、beliefから手札・山札・サイドの具体的な配置を1つ作り、完全情報ゲームとして探索できるようにする操作です。自分については既知の60枚デッキから公開カードと手札を差し引き、残りを山札と裏向きサイドへ配ります。相手についても推定60枚から公開カードを引き、残りを手札、山札、サイドへ配ります。

局面ごとのseedは、turn、プレイヤー、先攻、step、ログ数、選択contextからSHA-256で作ります。同じ観測では同じ決定化を使うため、実行ごとの不必要な揺れを抑えます。

### policyとvalue

**policy**は各合法手の有望さ、**value**はその局面が最終的な勝利へどれだけ近いかを表す値です。モデルはゲーム全体の行動を直接1つ出すのではなく、cabtが提示した最大64個の合法手それぞれへスコアを付けます。

### PUCT

**PUCT**は、今まで高い価値を示した手の活用と、モデルが有望だと予測した未探索手の探索を両立する木探索規則です。本実装の概念式は次です。

```text
選択値 = 探索で得た平均value
       + 0.4 × sqrt(親の訪問数) × policy事前確率 / (1 + 子の訪問数)
```

訪問が少なくpolicyの高い手には探索ボーナスが付き、探索済みでvalueの高い手は平均価値によって再選択されます。24回探索した後、root直下で最も訪問された手を実行します。

## 3. モデルへ何を入力するか

### 局面encoder

局面は24個の疎なtokenへ変換します。主な情報は次のとおりです。

- 両者のベンチとバトル場にいるポケモン
- HP、道具、エネルギー、進化前カード
- 山札・手札・トラッシュ・ベンチ・サイドの枚数
- どく、やけど、ねむり、マヒ、こんらん
- トラッシュのカードID
- 自分の手札と60枚デッキ
- スタジアム
- ターン数と先後

カード集合はEmbeddingBagで128次元へまとめられ、1層のTransformer encoderが局面内の関係を処理します。全tokenの出力を平均して`tanh`を通した1値がvalueです。

### 合法手decoder

各合法手は、行動種別と対象カードを表すtokenになります。例は「手札のカードを使う」「特定ポケモンへエネルギーを付ける」「進化する」「特性を使う」「攻撃する」「ターンを終える」です。

decoderは局面encoderへattentionし、「この局面で、この対象へ、この操作をする」組合せを評価します。各候補の1値がpolicy logitになり、探索開始時の事前確率へ変換されます。

## 4. 1手が決まるまで

処理の流れは次のとおりです。

```text
obs_dict
  ↓ 公開zoneとログから相手カードを履歴へ追加
相手の60枚デッキ候補を選択・観測に合わせて補正
  ↓ 自分と相手の非公開zoneを1組サンプル
cabt SearchBeginで探索状態を作成
  ↓
Transformerがrootのvalueと各合法手policyを予測
  ↓
PUCTを24回実行
  ↓
最も訪問されたroot行動のoption index列を返す
```

モデルファイルがなければ明示的に`FileNotFoundError`で停止します。学習済みモデルがない状態をランダム行動で隠しません。belief復元だけが失敗した場合は旧互換の簡易非公開状態へ縮退しますが、その理由は診断情報へ保存されます。合法手が作れない場合だけ、cabtが保証した合法候補の先頭を決定的に返します。

## 5. デッキ戦略との接続

採用したcluster 05は、ロケット団のポケモンを早期に展開し、盤面の頭数、エネルギー循環、対面別アタッカーを結び付けるデッキです。

- ロケット団のタマンチュラ4枚とワナイダー4枚で主軸を安定させる。
- ワナイダーの「Charging Up」でトラッシュの基本エネルギーを毎ターン再利用する。
- ワナイダーの「Rocket Rush」は場のロケット団ポケモン数×30ダメージなので、展開自体が打点になる。
- ロケット団のプロトン、トランシーバー、アリアナ、Factoryで、ロケット団ポケモンと手札を継続供給する。
- ロケット団のフリーザーはBasicロケット団ポケモンへの攻撃効果を防ぎ、特殊効果で勝ち筋を崩されにくくする。
- ロケット団のミミッキュは相手のActiveがTeraなら相手の攻撃を利用する対面札になる。
- ロケット団のミュウツーexはロケット団ポケモン4体以上で攻撃可能になり、ベンチのエネルギーを最大2枚捨てて160から最大280ダメージへ伸ばす終盤札になる。
- シェイミはRule Boxを持たないベンチへの攻撃ダメージを防ぐ。

### 具体的な判断例

中盤にロケット団ポケモンが3体、手札に4体目とエネルギー、バトル場にワナイダーがいるとします。目先だけを見ると、すぐ攻撃して90ダメージを与える手が魅力的です。しかし4体目を先に出せばRocket Rushは120へ上がり、ミュウツーexの攻撃条件も満たし、次ターン以降の勝ち筋が増えます。一方でベンチを埋めると、相手のベンチ攻撃や呼び出しの標的も増えます。

モデルは現在のHP、場、手札、エネルギー、相手盤面を入力して各行動を評価し、PUCTは「4体目を出した後の相手応答」までcabtで進めます。その結果、単純な即時ダメージではなく、展開による将来打点とリスクを含む訪問数で行動を選びます。ただし24探索は浅く、必ず正しい長期計画を見付ける保証はありません。

## 6. 学習サンプルとモデル更新

### 自己対戦RL

自己対戦では、各局面について次を保存できます。

- encoder入力: その局面
- decoder入力: 合法手一覧
- policy教師: MCTSで更新された各候補の相対価値
- value教師: 終局勝敗と探索時valueを混ぜた値

終局の勝者には`+1`、敗者には`-1`、引き分けには`0`を与え、過去の局面へ逆向きに伝えます。valueはHuber loss、policyも候補手ごとのHuber lossで更新します。

### 模倣学習

公式episodeからは、実際に選ばれた合法手をpolicyの正解クラス、最終勝敗をvalue教師にします。日次ZIPを全展開せず、固定seedで選んだepisodeをshard化します。policyはcross entropy、valueはHuber lossです。

今回のtrainは2026-07-01〜17、validationは07-18〜20、test保留は07-21〜23です。モデル、optimizer、Python RNG、PyTorch RNG、epochをcheckpointへ保存するため、同じ状態から再開できます。

重要なのは、validation精度が上がっても対戦が強くなるとは限らないことです。今回もtop-1精度は37.96%から53.98%へ上がりましたが、対戦は4勝16敗でした。平均的な過去行動への一致が、採用デッキ固有の勝ち筋や探索中の分布外局面を改善しなかったと解釈し、模倣重みを棄却しました。

## 7. 採用しなかった方式

| 方式 | 棄却理由 |
|---|---|
| 3決定化 × 8探索 | 同じ総探索予算の1決定化 × 24探索へ4勝16敗。CPU予算を分散すると各探索木が浅くなった |
| 32探索 | 24探索へ9勝11敗。小規模比較で追加計算に見合う改善がなかった |
| beliefなしの旧決定化 | belief方式との比較は9勝11敗で差を証明できなかった。ただし旧方式は未知カードを固定IDで埋め、履歴と矛盾し得るため最終方式にはしなかった |
| 追加模倣学習 | validation精度改善に反して対戦4勝16敗 |
| 相手手番専用モデル | 主要5相手への小規模比較で8勝12敗 |
| MuZero型世界モデル | 2日・CPU中心ではデータ量、世界モデル誤差、評価量のリスクが高い |

## 8. どこまで証明できたか

belief処理そのものの勝率改善は証明できていません。強く支持されたのは、限られたCPU予算を1つの整合状態へ集中すること、デッキとcheckpointを組で選ぶこと、同一デッキ評価と各自デッキ評価を分けることです。beliefは「見たカードと探索仮定を矛盾させない」説明可能性・安定性の層として採用しています。

また、ローカル固定リーグはKaggle上位モデルへの勝利を意味しません。Kaggle実提出・ratingは未確認であり、アップロード後の実対戦で初めて第三段階を判定できます。
